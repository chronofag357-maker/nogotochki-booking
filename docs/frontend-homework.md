# Фронтенд сервиса записи — отчёт

Проект: «Ноготочки». Проверка 08.10.2026, локальный учебный сервер, вымышленные аккаунты.

## 1. Связь интерфейса с backend
Три логических экрана прототипа адаптированы в разделы одного public/index.html. Каталог услуг (#services) получает GET /api/services: name, duration, price. Вход (#auth) отправляет POST /api/login, регистрация — POST /api/register. Кабинет (#account) получает GET /api/me, GET /api/bookings и GET /api/notifications. Обработчики и безопасное заполнение DOM находятся в public/app.js, общая функция сетевых запросов — public/api.js. Это работающий адаптированный интерфейс, не пиксельная копия Claude-прототипа. Сессия в HttpOnly SameSite-cookie, запросы изменения дополнительно защищены CSRF-токеном; session token не возвращается в JSON и не хранится в localStorage.

## 2. Проверка источника данных
Без редактирования HTML/JS изменено имя услуги id=6 непосредственно в SQLite на «Ламинирование бровей — проверка БД 0810». После перезагрузки браузера в каталоге появился текст «Ламинирование бровей — проверка БД 0810 · 60 мин · 1800 ₽». Затем исходное название восстановлено. Интерфейс действительно получает данные базы через API, а не показывает копию прототипа.

## 3. Ошибка входа
Для существующего browser-client@example.test введён неверный учебный пароль. На экране дословно: «401: Неверный email или пароль». Ответ 401 формируется обработчиком POST /api/login; frontend показывает серверный текст через общий api.js и область role=status. При правильном пароле открыт кабинет «Учебный клиент»; после перезагрузки вход сохранён.

## 4. Два разных клиента
На 127.0.0.1 вошёл browser-client@example.test. В кабинете: «№1 · Маникюр с гель-лаком · Анна Ковалева · 2026-10-09 10:00–11:30 · 1800 ₽ · Подтверждена». На localhost зарегистрирован отдельный browser-second@example.test, имя «Второй учебный клиент». Это разные host-only cookie-сессии одного backend и одной базы. Его кабинет: «У вас пока нет записей». Запись первого клиента не появилась у второго. Дополнительный API-тест чтения чужого ID возвращает 404.

## 5. Найденная проблема и исправление
До доработки выбор услуги оставлял в списке всех мастеров, включая несовместимых. После выбора ламинирования можно было выбрать мастера маникюра и получить отказ от сервера. Добавлены фильтр GET /api/masters?service_id=6 и сброс старого времени/мастера при смене услуги. В браузере после выбора «Ламинирование бровей» теперь доступны только Марина Орлова и Елена Смирнова. Защита backend сохраняется независимо от фильтра; несовместимая пара в HTTP-тесте даёт 400. Устаревший ответ загрузки не заменяет выбор пользователя благодаря счётчику запросов.
